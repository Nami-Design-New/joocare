# مراجعة جودة مشروع Joocare

هذا الملف يجمع المشاكل والتحسينات التي ظهرت في مراجعة الكود، مع أمثلة وأثر كل نقطة والحل المقترح، ليكون مرجعًا مفهومًا قبل بدء الإصلاح.

## نطاق المراجعة وحدودها

- المراجعة شملت تنظيم الملفات، إعدادات المشروع، الستايلات، وعينات من الصفحات والخدمات والـ hooks.
- تم تشغيل ESLint على `src`، وكانت النتيجة وقت المراجعة: **11 خطأ و36 تحذيرًا**.
- نجح فحص TypeScript بعد إصلاح نوع `Applicant` في المهمة السابقة. هذا لا يعني أن كل وظائف المشروع مكتملة أو أن الـ lint ناجح.
- لم يتم تشغيل production build جديد ضمن هذه المراجعة، ولم تُراجع جميع الصفحات بصريًا أو تُختبر كل اتصالات الباك إند.
- تقييم الشكل النهائي والموبايل والتباين وسرعة الصفحات يحتاج مراجعة تشغيلية منفصلة.
- وجود خطر محتمل في الكود لا يعني إثبات حدوث اختراق. النقاط المشروطة موضحة أدناه.
- إعداد هذا التقرير لا يعني تنفيذ الإصلاحات المذكورة فيه.

مراجع مرتبطة: [قواعد المشروع](RULES.md)، [فجوات التصميم](DESIGN-GAPS.md)، [مراجعة الموبايل](mobile-sizing-audit.md)، [مراجعة الكاش](request-caching-audit.md). التقرير الحالي يركز على جودة التنفيذ ولا يستبدل هذه المراجع.

## 1. الأمان والخصوصية

### 1.1 طباعة استجابة تسجيل الدخول كاملة — P0

- **المشكلة:** `src/auth.ts` يحتوي على `console.log("USER FOUND:", data)` بعد طلب تسجيل الدخول. نفس الاستجابة يُستخرج منها access token.
- **الأثر:** قد تصل بيانات الحساب والتوكن إلى لوج السيرفر.
- **المطلوب:** إزالة طباعة الاستجابة، وتحديد الحقول المسموح تسجيلها، مع حجب التوكنات والبيانات الشخصية.
- **معيار الانتهاء:** نجاح وفشل تسجيل الدخول لا يسجلان كلمات مرور أو توكنات أو استجابات شخصية كاملة.

### 1.2 استخدام callbackUrl بدون تقييد محلي واضح — P0

- **المشكلة:** `src/proxy.ts` يقرأ `callbackUrl` من query string ويمرره إلى `new URL` ثم ينفذ redirect بدون تحقق ظاهر من نفس الـ origin.
- **الأثر:** يمكن أن تصبح وجهة التحويل خارج الموقع؛ المسار يحتاج تحققًا واختبارًا.
- **المطلوب:** قبول وجهات داخلية مسموحة فقط، والتحقق من origin والمسار، واستخدام وجهة افتراضية مناسبة للدور عند رفض القيمة.
- **معيار الانتهاء:** الروابط الخارجية أو غير الصالحة لا تنقل المستخدم خارج الموقع من هذا المسار.

### 1.3 عرض HTML بدون ضمان تنضيف ظاهر في الفرونت — P1

- **المشكلة:** `src/features/jobs/components/JobDescriptionCard.tsx` يعرض `job.description` باستخدام `dangerouslySetInnerHTML`، ولم يظهر sanitization لهذا المحتوى في الفرونت.
- **الأثر:** خطر XSS محتمل إذا كانت البيانات قابلة للإدخال وغير منظفة قبل وصولها. لا يمكن حسم ذلك من الفرونت وحده.
- **المطلوب:** التأكد من سياسة التنضيف في الباك إند، وتحديد tags وattributes المسموحة، وإضافة تنضيف موثوق عند الحاجة. إزالة الوسوم لاستخراج نص مختصر ليست بديلًا عن sanitization.
- **معيار الانتهاء:** المحتوى المنسق المسموح يظهر، والمحتوى التنفيذي وevent handlers والروابط الخطرة تُرفض أو تُزال.

### 1.4 حماية جلب الملفات غير موحدة — P1

- **الأمثلة:** `src/app/api/pdf-proxy/route.ts` و`src/app/api/download-cv/route.ts`.
- **المشكلة:** يوجد فحص للوجهة الأولى، لكن لا يظهر تحقق من وجهات redirects، أو timeout وحدود لحجم الاستجابة. تفاصيل التحقق تختلف بين المسارين.
- **الأثر:** سلوك غير متوقع مع الملفات الكبيرة أو البطيئة أو التحويل إلى وجهة غير مسموحة.
- **المطلوب:** سياسة مشتركة للبروتوكولات والدومينات والـ redirects والمهلة والحجم ونوع المحتوى، مع مراجعة صلاحيات الوصول إذا كانت الملفات خاصة.
- **معيار الانتهاء:** الحالات المرفوضة تتوقف برسالة وحالة HTTP واضحتين دون متابعة جلب غير مقيد.

## 2. تنظيم الملفات وحدود المسؤوليات

### 2.1 أسماء غير موحدة وأخطاء إملائية — P2

- **الأمثلة:** `accout-settings`، `forEmployers`، `shared-copmonents-page`، `formateDate.ts`.
- **الأثر:** صعوبة البحث وتوقع أسماء الملفات، واحتمالات تكرار المسؤوليات بأسماء مختلفة.
- **المطلوب:** اعتماد naming convention موحدة، وتصحيح الأسماء ضمن مهمة مخصصة. تغيير route عام يحتاج الحفاظ على الروابط القديمة عند اللزوم.

### 2.2 اختلاف تنظيم الـ features — P2

- **المشكلة:** `jobs` منظمة داخل `components/hooks/services/types`، بينما `contact` تحتوي مكونات مباشرة في الجذر، و`faq` تستخدم ملف `services.ts`.
- **الأثر:** مكان المسؤولية لا يكون متوقعًا عند الانتقال بين الأقسام.
- **المطلوب:** تطبيق تنظيم متناسب مع حجم الـ feature وقواعد المشروع، دون إنشاء مجلدات فارغة أو نقل شامل لمجرد التشابه.

### 2.3 shared يعتمد على features — P2

- **الأمثلة:** `src/shared/components/HeaderLayout.tsx` يستورد hook من company profile، ومكونات الهيدر تستورد auth وnotifications وcandidate profile.
- **الأثر:** الطبقة العامة مرتبطة بمنطق المنتج، وإعادة استخدامها أو تعديل feature قد يتطلب فهم أجزاء أخرى. هذا يخالف اتجاه الاعتماد المحدد في `RULES.md`.
- **المطلوب:** إبقاء UI العام مستقلًا، وتمرير البيانات والتصرفات عبر props، أو وضع أجزاء تركيب التطبيق في طبقة مناسبة.
- **ملاحظة:** الـ providers تحتاج قرارًا واضحًا لمكان تركيبها؛ لا ننقل كل منطق feature إلى shared لمجرد التخلص من import.

### 2.4 اعتماد مباشر على تفاصيل features أخرى — P2

- **الأمثلة:** `jobs` تستورد مكونات وtypes وseed data من assessments وprojects وtalent database.
- **الأثر:** تعديل ملف داخلي قد يكسر أكثر من feature، ويصعب فصل البيانات التجريبية عن التنفيذ الحقيقي.
- **المطلوب:** واجهات تصدير محددة للتكامل، ووضع المفاهيم المشتركة فعلًا في مكان مناسب. التكامل بين features ليس خطأ في ذاته.

### 2.5 كود قديم أو غير مستخدم — P2

- **المثال:** لم يظهر استخدام لـ `ApplicantRow` داخل `src` وقت البحث، لكنه تسبب في فشل type check بسبب نوع قديم محذوف.
- **الأثر:** ملفات لا تدخل في المسار الفعلي قد تظل تكسر البناء أو تربك المطور.
- **المطلوب:** حصر unused code والتحقق من الاستيرادات والاستخدامات الديناميكية قبل الحذف.
- **الحالة:** تم استرجاع `Applicant` لحل خطأ البناء السابق؛ احتياج المكوّن نفسه ما زال يحتاج حسمًا.

## 3. الديزاين سيستم

### 3.1 كثرة tokens بدون فصل واضح للأدوار — P2

- **الأمثلة:** `primary`، `assessment-primary`، `chat-primary`، `dashboard-primary` داخل `src/app/globals.css`.
- **الأثر:** يصعب معرفة متى نستخدم لون البراند ومتى نستخدم لون حالة أو لون مكوّن.
- **المطلوب:** تنظيم tokens إلى أساسيات، ومعانٍ مثل success/error/surface، ثم احتياجات المكونات الفعلية. اختلاف ألوان الأقسام ليس مشكلة إذا كان مقصودًا وموثقًا.

### 3.2 ألوان مباشرة خارج tokens — P2

- **الأمثلة:** `text-[#212529]` و`bg-[#E5E7EB]` في مكونات jobs، وألوان مباشرة في home وتخصيصات المكتبات.
- **الأثر:** تعديل الهوية والثيم يتطلب تغييرات متناثرة ويزيد اختلاف الألوان.
- **المطلوب:** ربط الألوان المتكررة بمعانٍ واضحة في tokens، مع السماح فقط بالاستثناءات المقصودة والموثقة.

### 3.3 تكرار تنفيذ حقول الفورم — P2

- **الأمثلة:** `src/shared/components/InputField.tsx`، و`src/shared/components/ui/input.tsx`، و`src/features/contact/Input.tsx`.
- **الأثر:** احتمالات اختلاف شكل الحقول وfocus ورسائل الخطأ وحالات disabled وربط labels.
- **المطلوب:** استخدام primitive واحدة وحقول مشتركة فوقها، مع variants للحالات المختلفة بدل تنفيذ موازٍ.

### 3.4 أنماط العناوين غير محددة بما يكفي — P2

- **الأمثلة:** `ProjectDetailsHeader` يستخدم حجمًا يصل إلى `28px` ووزن bold، بينما `SettingsPageHeader` يصل إلى `32px` ووزن semibold.
- **الأثر:** احتمال اختلاف التسلسل البصري بين الصفحات المتشابهة.
- **المطلوب:** تعريف أنماط page title وsection title وcard title والنص المساعد، مع استثناءات مقصودة. لا نحكم أن كل اختلاف خطأ قبل المقارنة البصرية.

### 3.5 globals.css يجمع مسؤوليات كثيرة — P2

- **المشكلة:** الملف يجمع tokens وlayout utilities وخلفيات وتخصيص FilePond وCKEditor، مع عدة `!important` وبعض selectors العامة.
- **الأثر:** صعوبة معرفة مصدر الستايل واحتمال تأثير تخصيص على أماكن غير مقصودة.
- **المطلوب:** فصل الأساسيات عن تكامل المكتبات، وتضييق نطاق selectors وتقليل overrides غير الضرورية.

### 3.6 دعم dark mode جزئي — P2 إذا كان ضمن النطاق

- **المشكلة:** توجد `.dark` لكن ألوان أقسام كثيرة لا تتغير، مع وجود `bg-white` مباشرة و`body-bg` فاتح في تعريف الثيم الداكن.
- **الأثر:** تفعيل الثيم قد ينتج أسطحًا ونصوصًا غير متناسقة.
- **المطلوب:** حسم هل الثيم الداكن مطلوب، ثم مراجعته على الصفحات والمكونات والحالات كلها قبل اعتباره مدعومًا.

## 4. اكتمال الوظائف وتجربة المستخدم

### 4.1 صفحات تستخدم بيانات تجريبية — P1

- **الأمثلة:** `RolesPage` تستخدم `sampleCompanyRoles`، وAI job match تستخدم preview data، وtalent database تستخدم preview hook.
- **الأثر:** ظهور الواجهة لا يعني اكتمال الوظيفة أو ارتباطها ببيانات الحساب.
- **المطلوب:** قائمة صريحة لكل feature توضح: جاهزة فعليًا، واجهة تجريبية، تنتظر API، أو خارج نطاق الإصدار.

### 4.2 رسالة نجاح لإرسال لم يحدث عبر API — P1

- **المثال:** `src/features/company-talent-database/hooks/useTalentDatabasePreview.ts`؛ دالة `previewSendMessage` تحدث العدد وتغلق النافذة فقط، والصفحة تستخدم العدد لعرض نجاح.
- **الأثر:** المستخدم قد يظن أن رسالة وصلت بالفعل.
- **المطلوب:** ربط العملية بـ API وإظهار النجاح بعد تأكيده، أو تمييز التجربة بوضوح وتعطيل الإرسال الحقيقي لحين اكتماله.
- **معيار الانتهاء:** لا تظهر رسالة نجاح لعملية لم يؤكدها النظام الحقيقي.

### 4.3 الشات يعتمد على state محلية — P1

- **المثال:** `src/features/chat/hooks/useChat.ts` يضيف الرسالة محليًا، مع بيانات preview في hooks الخاصة بالأدوار.
- **الأثر:** الكود الحالي لا يثبت إرسال الرسالة أو حفظها واسترجاعها بعد إعادة التحميل.
- **المطلوب:** ربط المحادثات والإرسال والتحديثات بالباك إند، مع حالات sending وfailed وretry ومنع تكرار الرسالة.

### 4.4 صفحة أمثلة المكونات ضمن routes التطبيق — P2

- **المثال:** `src/app/[locale]/(shared-layout)/shared-copmonents-page/page.tsx` تعرض صفحة أمثلة وبيانات تجريبية.
- **الأثر:** وجود أداة تطوير كصفحة منتج قد يربك المستخدم إذا وصلت إلى بيئة الإنتاج.
- **المطلوب:** جعل إتاحتها مقصودة ومقيّدة بالبيئة أو الصلاحيات المناسبة.

## 5. جودة الكود والـ Types

### 5.1 ملفات تجمع مسؤوليات كثيرة — P2

- **الأمثلة:** `JobPostStepOne.tsx` يحتوي أكثر من ألف سطر غير فارغ، و`PostJobForm.tsx` و`JobReviewPanel.tsx` و`BasicInfoForm.tsx` ملفات كبيرة أيضًا.
- **الأثر:** صعوبة التعديل والمراجعة وفهم أثر تغيير بسيط.
- **المطلوب:** فصل الأقسام ذات المعنى، ومنطق الخطوات، وتحويل البيانات، والتحقق. الهدف فصل المسؤوليات، وليس تقليل عدد السطور فقط.

### 5.2 فحص ESLint غير ناجح — P1

- **النتيجة وقت المراجعة:** 11 خطأ و36 تحذيرًا في `src`.
- **أمثلة الأخطاء:** `no-explicit-any` في `useGetCompanyJob` و`typed-zod-resolver`، و`react-hooks/refs` في `useInfiniteScroll` و`DrawerScrollableContent`.
- **المطلوب:** إصلاح الأخطاء، ومراجعة التحذيرات حسب أثرها، ثم جعل الفحص شرطًا تلقائيًا لقبول التغييرات.
- **معيار الانتهاء:** فحص lint ينجح بدون تعطيل القواعد لإخفاء المشاكل.

### 5.3 شكل استجابات API غير محسوم في بعض الأماكن — P2

- **المثال:** `src/features/jobs/hooks/useGetCompanyJob.ts` يحاول قراءة أكثر من مسار للاستجابة باستخدام `any`.
- **الأثر:** أخطاء العقد بين الفرونت والباك قد تختفي حتى تظهر كبيانات ناقصة في الشاشة.
- **المطلوب:** تعريف response types واضحة وتحويلها داخل service إلى model ثابت للواجهة، والتحقق عند الحدود الحساسة.

### 5.4 تكرار lookup hooks — P2

- **الأمثلة:** `useGetCountries` و`useGetDomains` متشابهان في fetch والبحث والـ pagination، ويوجد أصلًا `useInfiniteLookup`.
- **الأثر:** إصلاح pagination أو معالجة الخطأ يحتاج تحديث نسخ متعددة.
- **المطلوب:** مراجعة صلاحية الـ hook المشتركة وتوحيد السلوك المتكرر مع الإبقاء على اختلافات الموارد الفعلية.

### 5.5 props مقبولة بدون تنفيذ السلوك المتوقع — P2

- **المثال:** `src/features/jobs/components/DescriptionSection.tsx` يقبل `title` لكن عنصر عرض العنوان معلق.
- **الأثر:** المستدعي يمرر عنوانًا لا يظهر، وقد يتأثر تسلسل المحتوى.
- **المطلوب:** إعادة العنوان إذا كان مطلوبًا، أو إزالة الـ prop وتحديث الاستخدامات إذا تغير دور المكوّن.

## 6. العربي والـ Accessibility

### 6.1 خط العربي غير محدد بوضوح — P2

- **المثال:** `src/app/[locale]/layout.tsx` يحمل Outfit وNoto Sans بإعدادات لاتينية، ويطبق Outfit على body لكل اللغات.
- **الأثر:** العربي قد يعتمد على fallback يختلف حسب الجهاز، ما يؤثر في المقاسات والهوية.
- **المطلوب:** اختيار خط عربي صريح ومتوافق مع الإنجليزي، وربطه باللغة والتحقق من الأوزان والتفاف النصوص.

### 6.2 تداخل main landmarks — P2

- **الأمثلة:** الـ root layout يحتوي `main`، والـ shared layout يحتوي `main` وفي داخله `main`، مع تكرارها في صفحات أخرى.
- **الأثر:** بنية المحتوى الأساسي غير واضحة لأدوات الوصول.
- **المطلوب:** main واحدة ظاهرة للمحتوى الأساسي، واستخدام `div` أو `section` لباقي الحاويات حسب المعنى.

### 6.3 بعض labels غير مرتبطة بالحقول — P2

- **المثال:** `src/features/contact/Input.tsx` يحتوي label بدون `htmlFor` وinput بدون `id`.
- **الأثر:** اسم الحقل ليس مرتبطًا به برمجيًا، والضغط على الاسم لا ينقل التركيز إليه.
- **المطلوب:** ربط label بالحقل، وربط رسائل الوصف والخطأ، والاستفادة من الحقول المشتركة.

### 6.4 نصوص fallback إنجليزية في مكونات عامة — P2

- **المثال:** `Try again` في `src/shared/components/RouteErrorFallback.tsx`.
- **الأثر:** قد تظهر تجربة مختلطة اللغة عند الخطأ حتى لو الصفحة الأساسية مترجمة.
- **المطلوب:** مراجعة حالات الخطأ والفراغ والتحميل وaria labels والتوست، وإكمال مفاتيح اللغتين.

## 7. الأداء والتحقق قبل الإطلاق

### 7.1 API wrapper لا يعرض signal أو timeout في options — P2

- **المثال:** `src/shared/lib/fetch-manager.ts`.
- **الأثر:** يصعب إلغاء طلب قديم أو تحديد مهلة له من المستدعي، خصوصًا مع البحث المتغير.
- **المطلوب:** دعم `AbortSignal` وسياسة timeout ومعالجة الإلغاء بشكل مختلف عن الخطأ الحقيقي.

### 7.2 سياسة تحديث البيانات عامة أكثر من اللازم — P2

- **المثال:** `src/shared/providers/tanstack-query/query-client-setup.ts` يعطل refetch عند mount وfocus وreconnect افتراضيًا.
- **الأثر:** موارد متغيرة قد تظل قديمة ما لم يحدث invalidation أو تحديث صريح. هذا خطر يعتمد على إعدادات كل query.
- **المطلوب:** سياسات حسب طبيعة المورد: lookups ثابتة نسبيًا، وحالات طلبات وإشعارات تحتاج تحديثًا أقرب.

### 7.3 مصدر التوقيت يختلف بين السيرفر والمتصفح — P1 للمواعيد الحساسة

- **الأمثلة:** `getTimeZone()` يرجع توقيت بيئة التنفيذ، بينما `MainProviders` يضبط next-intl على UTC.
- **الأثر:** احتمال اختلاف عرض المواعيد أو إرسال timezone مختلفة حسب مكان تنفيذ الطلب، خصوصًا للتقييمات.
- **المطلوب:** تعريف مصدر توقيت المستخدم، وطريقة التخزين والتحويل والعرض، واختبار نفس الموعد عبر السيرفر والمتصفح.

### 7.4 غياب منظومة اختبارات وchecks داخل المستودع — P1

- **الملاحظة:** لا يوجد test runner مضبوط في `package.json`، ولم يظهر مجلد `.github` وقت المراجعة. قد توجد منظومة CI خارج المستودع؛ لم يتم التحقق منها.
- **الأثر:** اكتشاف الأخطاء يعتمد بدرجة كبيرة على التشغيل اليدوي، ونجاح build لا يختبر اكتمال رحلات المستخدم.
- **المطلوب:** checks تلقائية للـ lint والـ types والـ build، واختبارات ذات قيمة للمسارات الأساسية: الدخول، نشر وظيفة، التقديم، والصلاحيات والتقييمات الحساسة.
- **ملاحظة:** لا نحتاج اختبارات شكلية لكل مكوّن أو اختبارات تكرر تفاصيل التنفيذ.

## 8. خطة الإصلاح المقترحة

| الترتيب | نطاق العمل | نتيجة يمكن مراجعتها |
| --- | --- | --- |
| 1 | اللوج والـ redirects ومراجعة HTML وجلب الملفات | منع تسجيل البيانات الحساسة، وتقييد الوجهات، وتوثيق حدود الثقة |
| 2 | حصر الوظائف التجريبية | جدول جاهزية واضح ومنع نجاح العمليات الوهمية |
| 3 | أخطاء lint والتحقق التلقائي | checks ناجحة ومتكررة لكل تغيير |
| 4 | الفورم والعناوين والـ tokens | مكونات وأنماط موحدة، مع مراجعة عربية وإنجليزية |
| 5 | الملفات الكبيرة والاعتمادات والكود القديم | مسؤوليات أوضح وتغييرات أصغر وأسهل مراجعة |
| 6 | مراجعة تشغيلية وبصرية | نتائج فعلية للموبايل والـ RTL والوصول والأداء والرحلات الأساسية |

تنفذ التغييرات على دفعات صغيرة قابلة للمراجعة. تغيير الأسماء والـ routes أو نقل المجلدات يتم كمهمة واضحة، وليس ضمن إصلاح غير متعلق.

## 9. ما الذي يحتاج مراجعة لاحقة؟

- مقارنة الشاشات الفعلية بالتصميم المرجعي، دون الاكتفاء بوجود المكونات في الكود.
- اختبار الموبايل والتابلت والديسكتوب بالعربي والإنجليزي، مع النصوص الطويلة والبيانات الفارغة.
- قياس الأداء الفعلي قبل اتهام مكتبة أو مكوّن بالتسبب في البطء.
- تأكيد عقود API وسياسة تنضيف HTML وصلاحيات الملفات مع الباك إند.
- اختبار رحلات الدخول والتسجيل ونشر الوظائف والتقديم والتقييمات بعد الربط الحقيقي.
- تحديث حالة كل بند بالأدلة بعد تنفيذه؛ إعادة صياغة الكود وحدها لا تكفي لإغلاق مشكلة سلوكية.

المشروع لا يحتاج إعادة كتابة شاملة بناءً على هذه الملاحظات. المطلوب هو تطبيق القواعد الموجودة باتساق، وإكمال الربط الحقيقي للوظائف التجريبية، والتحقق من النتيجة أثناء التشغيل.
