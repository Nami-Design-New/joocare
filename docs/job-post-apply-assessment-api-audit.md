# فلو إضافة الوظيفة والأسئلة والتقييم: الربط الحالي والناقص

تاريخ المراجعة: 17 نوفمبر 2026. آخر تحديث للتنفيذ والتحقق: 19 نوفمبر 2026.

## حالة التنفيذ — ابدأ من هنا عند الاستكمال

| الجزء                                                     | الحالة                                                               |
| --------------------------------------------------------- | -------------------------------------------------------------------- |
| 1. مكتبة التقييمات عند الشركة (تصنيفات + تقييمات + أسئلة) | **تم الربط وتم اختباره في المتصفح**                                  |
| 2. Post Job: اختيار التقييم في الخطوة الأولى              | **تم** — اختُبر في المتصفح                                           |
| 3. Post Job: أسئلة التقديم في الخطوة الثانية              | **تم الربط** — ينتظر نقاط الباك                                      |
| 4. المعاينة والمسودة والنشر والتعديل                      | **تم استكمال الفرونت واختبار المتصفح** — بقي تحقق الحفظ الحي النهائي |
| 5. المرشح: عرض الوظيفة وإرسال إجابات أسئلة التقديم        | **نُفّذ واختُبر بمحاكاة الطلبات** — ينتظر اختبار حساب مرشح حي |
| 6. دعوة التقييم بعد التقديم / الإسناد اليدوي              | لم يبدأ — يحتاج رد الـ backend                                       |
| 7. المرشح: أداء التقييم حتى التسليم                       | لم يبدأ — يحتاج رد الـ backend                                       |
| 8. حالة التقييم للمرشح ومراجعة الشركة للنتائج             | لم يبدأ — يحتاج رد الـ backend                                       |

الأجزاء السابقة محفوظة في سجل Git. تغييرات فلو تقديم المرشح محلية؛ لم يُنشأ لها commit في جلسة التنفيذ.

### استكمال فلو المرشح — 19 نوفمبر 2026

- أُلغيت أسئلة وتقييم التقديم التجريبيان. غياب الأسئلة يفتح اختيار CV مباشرة.
- أُضيف تحويل `questions` إلى أسئلة المرشح بالمعرّفات الأصلية للسؤال والإجابات، مع Required/Optional والتحقق من الاختيارات؛ لا تُمرّر علامة الإجابة الصحيحة إلى خيارات النموذج.
- أصبح `POST U/jobs` يرسل JSON: `job_id` و`cv` بمسار الملف المحفوظ و`answers: [{question_id, answer_ids}]`. الأسئلة الاختيارية غير المجابة لا تُرسل.
- مُنع تكرار الإرسال والضغط أثناء رفع CV، ويظل النموذج مفتوحًا عند فشل الطلب. بعد النجاح يُحدّث عرض الوظيفة وبيانات وظائف الشركة المخزّنة في query cache، وتُقرأ صفحات التقديمات من السيرفر عند فتحها.
- تأكيد النجاح عام حاليًا: لا ينشئ دعوة أو تاريخ إرسال أو صلاحية 72 ساعة أو رابط تقييم من بيانات محلية. انتظار استجابة التقديم الفعلية لربط الدعوة.
- **التحقق:** اختبار المتصفح بمحاكاة حساب المرشح وطلبات profile/submit، دون إنشاء تقديم حي: CV البروفايل، وظيفة بلا أسئلة، فشل 422 ثم إعادة المحاولة، والضغط مرتين أرسل طلبًا واحدًا. اختبارات تنفيذ مباشرة للتحويل والتحقق أثبتت معرّفات إجابات Yes/No، الإلزام والاختياري والمتعدد، وصيغ CV وJSON ورفض المعرّفات غير الرقمية. TypeScript وESLint للملفات المعدّلة نجحا؛ lint العام فيه 9 أخطاء و34 تحذيرًا سابقة خارج النطاق.
- **المتبقي لإكمال المرشح:** حساب مرشح ووظيفة/دعوة اختبار، استجابة قراءة أسئلة الوظيفة، استجابة نجاح التقديم والدعوة، وعقود قراءة/بدء/إجابة/إنهاء المحاولة. الحساب المتاح حساب شركة؛ طلبات التقييم المحمية أعادت 401. قراءة `GET U/jobs/327` أعادت تفاصيل بلا `questions` أو `assessment_id` رغم وجودهما في قراءة الشركة. لم يُفترض شكل استجابة غير متاح ولم تُغيّر صفحة التقييم التجريبية بعد.
- نقاط الشركة المتبقية (حفظ Required/Optional للقالب حيًا و`mark` وغيرها) **مؤجلة بطلب المستخدم**.

### تحقق حي بحساب المرشح — 19 نوفمبر 2026

**تحديث لاحق لنفس الجلسة:** أصبحت `questions` موجودة في `GET U/jobs/327`: الأسئلة 37 و38 و39 و40 بأنواعها وإلزامها، لكن بدون `answers` لأي سؤال. سبب خطأ 500 كان رفض mapper للاختيارات الناقصة أثناء عرض الصفحة. صُحح ذلك: الصفحة تعرض تفاصيلها واللوج المؤقت، ويمنع زر التقديم فتح نموذج ناقص برسالة مترجمة، بدل انهيار التفاصيل أو تجاوز الأسئلة. العائق المتبقي الآن هو إعادة `answers: [{id, answer}]` لكل سؤال، ثم استجابة الدعوة. اختُبر أن الصفحة تعيد 200 وأن محاولة التقديم في هذه الحالة لا ترسل POST. السجل التالي يصف القراءات الأقدم قبل ظهور `questions`.

- تم تسجيل الدخول بحساب مرشح حقيقي، وأعاد `GET U/auth/profile` استجابة 200 وCV محفوظًا. بيانات الدخول ليست محفوظة في المستودع.
- `GET U/jobs/327` أعاد 200 و`is_applied: false`، لكن بدون `questions` أو `assessment_id` أو `assessment`. `GET U/jobs/324` يعاني غياب نفس حقول الأسئلة والتقييم.
- جُرّب التقديم من المتصفح على وظيفة الاختبار 327 باستخدام CV البروفايل. أعاد `POST U/jobs` الحالة **422** مع `data.missing_questions: ["Do you have ICU experience?"]` ورسالة «يرجى الإجابة عن جميع الأسئلة المطلوبة.» لم يُنشأ تقديم؛ بقي النموذج مفتوحًا وظهر خطأ السيرفر.
- `GET U/assessments/5` و`GET U/assessments/1` أعادا **404**: `You have not been invited to this assessment.` مشكلة 401 السابقة انتهت بعد الدخول بالدور الصحيح؛ لا توجد دعوة اختبار متاحة لهذين التقييمين.
- **العائق المؤكد الآن:** إعادة أسئلة الوظيفة إلى المرشح مع `id`, `question`, `type`, `is_required`, `answers: [{id, answer}]`، ثم إتاحة دعوة تقييم اختبار بعد التقديم أو رابط دعوة موجود. لا يمكن استخراج معرّفات الإجابات من `missing_questions` لأنها أسماء أسئلة فقط. لم تُرسل إجابات مخمّنة ولم تُبدأ محاولة تقييم.

**مرجع الحالة الحالية:** جدول الحالة وقسم الاستكمال أعلاه وقسم «عقد أسئلة التقديم المؤكد» أدناه. القوائم القديمة تصف المراجعة الأصلية قبل الربط؛ الأقسام 5 و6 موضّح بها فرق التنفيذ الحالي.

قبل كتابة أي كود: اقرأ [RULES.md](RULES.md) و`AGENTS.md`، واتبع نفس نمط `src/features/company-assessments` الذي نُفّذ في الجزء 1 (services + hook لكل query/mutation + query keys في constants + ترجمة en/ar + `tsc` و`eslint`).

هذا الملف يجمع الجزأين **7: أسئلة التقديم والتقييم المرتبط** و**8: أداء التقييم** من [حصر المرشح](candidate-static-data-audit.md)، مع الجزء السابق لهما عند الشركة والنتائج التي تعود إليها. الغرض هو تحديد العمل المطلوب لإكمال الفلو من البداية للنهاية، وليس تنفيذ الربط في هذا التعديل.

## الخطة الكاملة للفلو — إيه الناقص (بدون endpoints)

الفلو المطلوب من الأول للآخر: الشركة تعمل assessment ← تضيف وظيفة وتربط بيها الـ assessment وتضيف أسئلة التقديم ← المرشح يفتح الوظيفة ويعمل Apply Now (Step 1: إجابة أسئلة الوظيفة، Step 2: رفع/اختيار CV) ← المرشح يحل الـ assessment في `/candidate/assessment/[id]` ← الشركة تشوف الإجابات والنتيجة.

ربط كل نقطة بالـ endpoint المناسب من [الكولكشن](postman-collection-joocare) هيتعمل في الجلسة الجاية، نقطة نقطة مع المستخدم.

### أ. الشركة: إنشاء الـ assessment — تم

- [x] التصنيفات، والتقييمات، والأسئلة، والإنشاء بالـ 3 steps، والتعديل والحذف (التفاصيل في الجزء 1).
- [ ] صفحة تفاصيل الـ assessment (زر العين في الكارت) و`external-invitations`: لسه بيانات تجريبية.

### ب. الشركة: إضافة وظيفة `/company/post-job` (3 steps)

**Step 1 — تفاصيل الوظيفة + ربط الـ assessment**

- [x] قوائم المكتبة والتصنيف والـ assessment من الـ API (تفاصيل في الجزء 2).
- [x] زرار المعاينة و`AssessmentPreviewDialog` بالـ assessment الحقيقي وأسئلته.
- [x] نافذة "Assessment fit" من `GET C/assessments/{id}`.
- [x] التعديل / المسودة: القسم مقفول ويعرض الـ assessment المحفوظ من `assessment_id`.
- [ ] اختبار في المتصفح (إنشاء بـ assessment وبدونه، رجوع للخطوة الأولى، مسودة، تعديل، عربي/إنجليزي، موبايل).
- (باقي حقول Step 1 مربوطة بالفعل.)

**Step 2 — الوصف والمهارات وأسئلة التقديم**

- [ ] قوالب الأسئلة (Template chips) ثابتة في الكود؛ لازم تيجي من السيرفر بالـ IDs الحقيقية.
- [ ] الأسئلة بتتبعت بشكل غلط (`screening_questions` كـ JSON واحد)؛ لازم تتبعت بالشكل المعتمد: قوالب مختارة + أسئلة مخصصة.
- [ ] نقاط محتاجة تتحسم: درجة السؤال `mark` وإلزام القالب موجودين في الواجهة ومش واضح إن السيرفر بيدعمهم، وقيم أنواع الأسئلة، وإزاي تتحذف كل الأسئلة.
- [ ] قراءة الأسئلة المحفوظة عند التعديل / المسودة من غير ما تضيع IDs أو إجابات.
- [ ] AI JD Builder: محلي بالكامل — مؤجّل، مش جزء من الفلو ده.
- (الوصف والمهارات مربوطين بالفعل.)

**Step 3 — المعاينة والنشر**

- [ ] المعاينة بتعرض الأسئلة من الفورم والـ assessment من بيانات تجريبية (`getLinkedAssessment`)؛ لازم تعرض اللي اتحفظ فعلًا.
- [ ] التأكد إن المسودة والنشر مش بيضيعوا الأسئلة أو الـ assessment ومش بيكرروهم.
- (حفظ المسودة والنشر نفسهم مربوطين.)

**بعد النشر — صفحة الوظيفة عند الشركة**

- [ ] كارت المرفقات في تفاصيل الوظيفة (`JobAttachmentsCard`) بيعرض معاينة الـ assessment من بيانات تجريبية.

### ج. المرشح: التقديم على الوظيفة (Apply Now)

- [ ] تفاصيل الوظيفة مربوطة، بس `JOB_APPLY_PREVIEW_ENABLED = true` بيعرض 9 أسئلة تجريبية و assessment تجريبي لو الوظيفة مفيهاش. لازم يتقفل، ووظيفة من غير أسئلة أو assessment تبقى حالة طبيعية.
- [ ] **Step 1 (إجابة أسئلة الوظيفة):** تحويل أسئلة الوظيفة الحقيقية (النوع والاختيارات والإلزام) للفورم، بدل الشكل المحلي.
- [ ] **Step 2 (CV):** مربوط (CV البروفايل أو رفع جديد) — يتأكد بس إنه بيتبعت صح مع الإجابات.
- [ ] الإرسال: الإجابات بتتبعت بشكل غلط (`screening_answers` بـ IDs محلية)؛ لازم تتبعت بالشكل المعتمد بـ IDs الأسئلة والإجابات الحقيقية.
- [ ] بعد النجاح: مودال "تم التقديم" بياخد وجود الـ assessment ووقت الإرسال ومدة الرابط (72 ساعة) من الواجهة؛ لازم ييجوا من رد السيرفر / الدعوة الحقيقية.
- [ ] رابط "ابدأ الـ assessment" مبني على ID الـ assessment بس؛ لازم يتحدد هو ID إيه (assessment / دعوة / محاولة).
- [ ] تحديث بيانات الوظيفة وقائمة التقديمات بعد التقديم (حاليًا `hasApplied` محلي بس).

### د. المرشح: حل الـ assessment `/candidate/assessment/[id]`

- [ ] الصفحة كلها تجريبية: البيانات من `getCandidateAssessmentPreview`، والحالة من `?state=`، والبدء والإجابات والتسليم في `useState`.
- [ ] شاشة المقدمة: بيانات الـ assessment الحقيقية (العنوان، المدة، درجة النجاح، عدد الأسئلة، الشركة).
- [ ] زرار البدء: يبدأ محاولة حقيقية أو يكمّل محاولة قديمة.
- [ ] الأسئلة: حفظ كل إجابة على السيرفر قبل الانتقال، ومعالجة الفشل وإعادة المحاولة.
- [ ] التايمر: من وقت السيرفر، مش `Date.now()`، ويستحمل refresh.
- [ ] التسليم: عند آخر سؤال أو انتهاء الوقت — **مفيش طريقة تسليم واضحة لسه، محتاج رد الباك**.
- [ ] الحالات: منتهي / اتحل قبل كده / مش متاح — من السيرفر بدل `?state=`.
- [ ] عرض صور الأسئلة لو موجودة (نموذج سؤال المرشح مفيهوش حقل للمرفقات).

### هـ. إكمال الحلقة

- [ ] المرشح — صفحة التقديمات: حالة الـ assessment ورابطه معطّلين بالتعليقات (`ApplicationStatus`)؛ لازم يتفعّلوا بالبيانات الحقيقية عشان "هعمل الـ assessment بعدين" يشتغل.
- [ ] الشركة — قائمة المتقدمين: نافذة إجابات أسئلة التقديم بتعرض `CANDIDATE_ANSWERS_PREVIEW` لكل المرشحين؛ لازم تعرض إجابات المرشح الحقيقية.
- [ ] الشركة — نتائج الـ assessment وتفاصيل محاولة المرشح (`/company/assessments-results`): تجريبية بالكامل.
- [ ] الإسناد اليدوي للـ assessment وإرساله بالإيميل، وPause/Resume: محليين.

### ترتيب الشغل المقترح

1. ب / Step 1: ربط الـ assessment بالوظيفة.
2. ب / Step 2: أسئلة التقديم.
3. ب / Step 3 + صفحة الوظيفة: المعاينة والمسودة والنشر والتعديل.
4. ج: التقديم بالإجابات والـ CV.

## النطاق ومصدر الحكم

- البداية: `/en/company/post-job`، وكذلك استكمال مسودة بـ `?jobId=` وتعديل وظيفة بـ `?editId=`.
- تجهيز مكتبة التقييمات وأسئلتها، ثم اختيار تقييم للوظيفة وإضافة أسئلة التقديم ونشر الوظيفة.
- عرض الوظيفة للمرشح، تقديم الإجابات وCV، فتح التقييم، بدء المحاولة والإجابة والتسليم.
- ظهور حالة التقييم للمرشح، ورؤية الشركة لإجابات التقديم ونتيجة التقييم.
- مرجع الطلبات: [الكولكشن](postman-collection-joocare)، خصوصًا مجلدات `Company/Jobs` و`Company/Assessment categories` و`Company/Assessments` و`Company/questions` و`Company/question-templates` و`User/applications` و`User/assessments`.

المراجعة مبنية على **الكود وملفات الطلبات المحلية**. لم تُنشأ وظيفة أو دعوة أو محاولة على السيرفر، ولم تُختبر استجابات API حية. ملفات الطلبات التي تمت مراجعتها لا تتضمن عقود استجابة كافية لتأكيد شكل كل حقل؛ لذلك نميّز بين:

- **مربوط:** يوجد طلب API في التنفيذ، دون ضمان نجاحه في التشغيل.
- **ربط جزئي / اختلاف عقد:** الطلب موجود لكن هناك فرق واضح عن مثال الكولكشن أو جزء من التدفق ما زال محليًا.
- **غير مربوط:** التنفيذ الحالي يعتمد على fixtures أو state محلية.
- **غير موثّق:** لم يوجد في الكولكشن طلب أو تفاصيل كافية للعملية؛ لا يعني ذلك الجزم بأن الـ backend لا يدعمها.

## 1. تجهيز التقييم عند الشركة — تم

**الحالة:** مربوط بالكامل واختُبر في المتصفح بحساب شركة (عرض، فلتر، إضافة/تعديل/حذف تصنيف، إنشاء تقييم بالـ 3 steps، تعديل تقييم وسؤال، حذف تقييم، العرض بالعربي). كل الطلبات رجعت 2xx.

### الصفحات وما تستخدمه

| الصفحة / المكان                                     | الـ Endpoint                                                                                    |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------- |

### قرارات وعقود مؤكدة

- بعد step 1 يُضاف `?assessmentId=` بـ `window.history.replaceState` (وليس `router.replace`) حتى لا يُعاد تركيب الصفحة ويضيع الـ step.
- زر الإنشاء الأخير في step 3 لا يرسل طلبًا؛ كل شيء محفوظ مسبقًا. لو خرج المستخدم في المنتصف يبقى التقييم على السيرفر — الـ backend يتعامل معه.
- أنواع الأسئلة من `GET C/questions/types`: `yes_no` / `single_choice` / `multi_choice` (مُحوّلة داخليًا إلى `yes-no` / `single-choice` / `multiple-choice`).
- `yes_no` يُرسل كباقي الأنواع: `answers[0][answer]=yes` و`answers[1][answer]=no` مع `is_correct`.
- المرفق: `has_file` + `files[]`، والاستبدال/الحذف يرسل `delete_file_ids[]`. لا تعتمد على `has_file` في الاستجابة (رجع `false` مع وجود ملف) — اعتمد على `files`.
- `created_at` يرجع نصًا نسبيًا ("23 minutes ago")، ويُعرض كما هو.
- البحث يُرسل `search` كـ query param ولا يُكتب في URL الصفحة.

### ما زال ثابتًا أو ناقصًا في هذا الجزء

- عدد التقييمات في كارت التصنيف، وAssociated Jobs وExternal Invitations في كارت التقييم: **قيم ثابتة بجانبها `#`** في الواجهة (الثوابت في `constants/assessment-queries.ts`) لحين إرجاعها من الـ backend.
- Pause/Resume: يعرض "coming soon" — لا يوجد endpoint.
- ترتيب الأسئلة: قائمة `questions` ترجع الأحدث أولًا، و`assessments/{id}` يرجع الأقدم أولًا؛ يلزم توحيد الترتيب من الـ backend.
- صفحة تفاصيل التقييم `/company/assessments/{categoryId}/{assessmentId}` (زر العين في الكارت) و`external-invitations` ما زالت على البيانات التجريبية.
- لم يُختبر في المتصفح: رفع صورة لسؤال واستبدالها، وصفحة تصنيف Joocare (لا توجد تصنيفات Joocare على السيرفر).
- `categorySeeds` و`assessmentSeeds` ما زالت مستخدمة في Post Job (`useAssessmentOptions`) وفي نوافذ الإسناد وصفحة التفاصيل — تُزال عند ربط تلك الأجزاء.

## 2. الشركة: Post Job — اختيار التقييم في الخطوة الأولى

**الموجود:** بيانات الوظيفة الأساسية تُرسل إلى `jobs-step-one`، وحقل `assessment_id` موجود في الخدمة وفي مثال الكولكشن. معظم lookup fields، مثل المسمى والدولة والمدينة ونوع العمل والتصنيف والخبرة والمؤهلات والعملات، مرتبطة بالفعل. هذه الخطوة ليست static بالكامل.

**الناقص:**

- `useAssessmentOptions` يستخدم `categorySeeds` و`assessmentSeeds` لتعبئة المكتبة والتصنيف والتقييم؛ المعرّفات الحالية مثل `company-0-1` تجريبية، ولا تصلح بديلًا لمعرّفات السيرفر.
- نافذة تأكيد ملاءمة التقييم تعرض عنوانًا وعدد أسئلة من fixtures؛ هي تأكيد UI، وليست طلب تحليل ملاءمة فعليًا.
- مصدر المكتبة عند تحميل وظيفة للتعديل يُستنتج بالبحث في `categorySeeds`؛ يحتاج بيانات حقيقية أو mapper معتمد.
- معاينة الأسئلة والدرجة والمدة تحتاج تفاصيل التقييم الفعلي وأسئلته.
- يلزم التحقق من أن اختيار تقييم أو إزالته يُحفظ ويعود في قراءة الوظيفة، بما في ذلك قبول القيمة الفارغة لإلغاء الربط. لا يكفي وجود `assessment_id` في FormData.
- مثال التعديل الشامل `Company/Jobs/التعديل (خطوة واحدة).yml` لا يتضمن `assessment_id`، رغم أن الكود يرسله. يلزم تأكيد عقد تعديل الربط وإلغائه في هذا الوضع أيضًا.

**الحالة (18 نوفمبر 2026): تم الربط واختُبر في المتصفح في جلسة التنفيذ السابقة.**

**قاعدة العمل المعتمدة:** الـ assessment يتحدد مرة واحدة عند إنشاء الوظيفة (`jobs-step-one`) ولا يتغير بعدها: لا إضافة ولا تغيير ولا حذف، سواء كانت الوظيفة مسودة أو منشورة، وحتى عند الرجوع للخطوة الأولى أثناء الإنشاء.

**عقود مؤكدة بطلبات حية (الوظيفة التجريبية 327، مسودة مربوطة بـ assessment 5):**

- `GET C/jobs/{id}` يرجع `assessment_id` فقط، بدون object `assessment`، والأسئلة في `questions` (وليس `screening_questions`).
- `jobs-update-step-one` يتجاهل `assessment_id` تمامًا (فاضي، `null`، `0`، أو ID آخر)، ويحفظ باقي الحقول. ده متوافق مع القاعدة.
- `GET C/assessments/{id}` يرجع `category: { id, name, is_global }`، ومنه تُعرف المكتبة والتصنيف.

**التنفيذ:**

- المكتبة: Joocare / الشركة ثابتة. التصنيفات: `global-assessment-categories` أو `assessment-categories` حسب المكتبة (`useGetAssessmentCategories` مع `enabled`). التقييمات: `GET C/assessments?category_id=` (infinite) عبر `useGetCategoryAssessmentOptions`.
- المعاينة: `AssessmentPreviewDialog` يستخدم `useGetAssessment` ويعرض `AssessmentReviewStep` ومعاينة السؤال من الـ builder.
- حقل `assessmentLocked` في الفورم: `true` لأي وظيفة محمّلة أو بعد نجاح `jobs-step-one`. وقتها `LockedAssessmentFields` يعرض القيم للقراءة فقط، والتحقق من حقول الـ assessment يتوقف، و`assessment_id` لا يُرسل.
- `JobAttachmentsCard` (المعاينة وصفحة الوظيفة عند الشركة) يستقبل `assessmentId` ويجيب العنوان من `useGetAssessment`، والزرار يفتح نافذة المعاينة.
- اتشال `useAssessmentOptions` و`getLinkedAssessment`. `job.assessment` و`JobLinkedAssessment` باقيين لفلو المرشح (الجزء 5).
- مكتبة Joocare فاضية على السيرفر حاليًا، فلم يُختبر هل `assessments?category_id=` يرجع تقييمات تصنيفاتها.
- endpoints في الكولكشن لم تكن مذكورة: `GET C/assessments-list` (id + name)، و`GET C/assessment-results` (يتطلب `assessment_category_id`) و`assessment-results/{id}` وnotes النتائج. دي تخص الجزء 8.

## 3. الشركة: Post Job — أسئلة التقديم في الخطوة الثانية

أسئلة التقديم جزء من الوظيفة، وتُحفظ حسب الكولكشن في **طلب الخطوة الثانية**. أما `Company/questions` فيخص أسئلة **التقييم** وطلبه يتطلب `assessment_id`؛ لا ينبغي استخدامه لحفظ أسئلة التقديم دون عقد يوضح ذلك.

### القوالب

> وصف المراجعة الأصلية قبل التنفيذ؛ الحالة المنفذة موثقة في «عقد أسئلة التقديم المؤكد».

- المصدر الحالي `SCREENING_QUESTION_TEMPLATES` في constants؛ معرّف القالب محلي مثل `education` أو `medical-license`.
- يوجد `GET C/question-templates-hints` و`GET C/question-templates` مع pagination وفلتر `ids[]` موثّق في الثاني، لكنهما غير موصولين في هذه الشاشة.
- اختيار الإجابة الصحيحة والإلزام وإضافة القالب يحدّث نموذج الصفحة فقط حتى محاولة إرسال الخطوة الثانية.
- المطلوب تحميل القوالب والتلميحات والاحتفاظ بالمعرّف الحقيقي وعلاقة كل hint بالقالب حسب الاستجابة، بدل افتراض تطابق معرّفات العرض المحلية مع معرّفات API.

### فرق عقد حفظ الأسئلة — أساسي قبل البدء

| النقطة                     | ما يفعله الكود الآن                      | ما يوثّقه الكولكشن                                                               |
| -------------------------- | ---------------------------------------- | -------------------------------------------------------------------------------- |
| القوالب والأسئلة المخصصة   | حقل واحد `screening_questions` يحوي JSON | مجموعتان من حقول multipart: `question_templates` و`custom_questions`             |
| القالب المختار             | `templateId` ضمن كائن محلي               | `question_templates[i][id]`                                                      |
| إجابة القالب الصحيحة       | `correctOptionIds` مثل `['yes']`         | `question_templates[i][correct_answer]` بقيمة `yes` أو `no`                      |
| نص السؤال المخصص           | `question`                               | `custom_questions[i][question]`                                                  |
| إلزام السؤال               | `required`                               | `custom_questions[i][is_required]` بقيمة `1` أو `0`                              |
| نوع السؤال                 | `single` أو `multi` أو `yes-no`          | المثال يذكر `custom_questions[i][type] = multi_choice`؛ بقية القيم تحتاج تأكيدًا |
| الخيارات والإجابات الصحيحة | `options` و`correctOptionIds`            | `custom_questions[i][answer][j][answer]` و`[is_correct]`                         |
| الدرجة `mark`              | موجودة في نموذج السؤال المحلي            | لا يوجد مقابل موثّق لها في مثال أسئلة التقديم                                    |

**تنبيهات عقد محددة:**

- مثال الخطوة الثانية يكرر `question_templates[0]` لقالبين مختلفين. يجب تأكيد التصحيح واستخدام فهارس مستقلة لكل قالب، وعدم نسخ التكرار كما هو.
- المثال يستخدم `answer` بالمفرد داخل `custom_questions`، بينما أسئلة التقييم تستخدم `answers` بالجمع. يُتبع العقد الخاص بكل endpoint.
- إلزام القالب ودرجة السؤال موجودان في UI، لكن المثال لا يوضح حفظ إلزام القوالب أو درجات أسئلة التقديم. يلزم تحديد هل يدعمهما السيرفر أو تعديل الواجهة وفق العقد المعتمد.
- إضافة / تعديل / حذف سؤال داخل النموذج يمكن أن تبقى محلية قبل الحفظ؛ الناقص هو serialization صحيح وحفظ فعلي واستعادة البيانات. يلزم تأكيد هل إرسال مجموعات الأسئلة يستبدلها بالكامل وكيف تُحذف كلها عند إرسال قائمة فارغة.

### عقد أسئلة التقديم المؤكد (18 نوفمبر 2026)

اتأكد بطلبات حية على الوظيفة التجريبية 327، واتجرّب في المتصفح.

- القوالب: `GET C/question-templates-hints?job_id={jobId}` يرجع `{ id, hint, is_used }` وهي الـ chips. اتأكد في 19 نوفمبر أن `is_used` يظهر فقط عند إرسال `job_id`. علامة الاختيار ومنع التكرار يعتمدان عليه مع القوالب المضافة محليًا. معرّف الوظيفة يُمرر من الفورم حتى بعد إنشاء الخطوة الأولى، ويدخل في query key؛ نجاح حفظ الخطوة الثانية يعيد تحديث hints لهذه الوظيفة واللغة. عند اختيار قالب متاح نجيب `GET C/question-templates?ids[]={id}` ويرجع `{ id, question }` (نفس الـ id).
- الحفظ في `jobs-step-two/{id}` للإنشاء **وللتعديل** (حتى بعد النشر، والوظيفة تفضل Open): `question_templates[i][id|correct_answer]` و`custom_questions[i][question|is_required|type|answer][j][answer|is_correct]`. الأنواع: `single_choice` / `multi_choice` / `yes_no`.
- كل إرسال يستبدل الأسئلة كلها بـ IDs جديدة. عدم إرسال `custom_questions` و`question_templates` يمسح الأسئلة كلها. إرسال `custom_questions=` فاضي يرجع 500.
- في تجربة 18 نوفمبر كان القالب يتحفظ `yes_no` و`is_required: true` دائمًا، ومن غير ربط بالقالب. هذه ملاحظة تاريخية؛ إعادة اختبار حفظ إلزام القالب بعد تحديث الباك ما زالت مطلوبة.
- الوصف لازم 500 حرف على الأقل.
- `POST C/jobs/{id}` (التعديل الشامل) يتجاهل الأسئلة؛ التعديل في الواجهة بقى `jobs-update-step-one` ثم `jobs-step-two`، واتشال `useUpdateJob` و`job-update-service`.

**قرارات المستخدم:** الـ hint هو اسم الـ chip؛ إلزام القالب و`mark` يتبعتوا ويستنوا دعم الباك؛ الباك يرجّع `template_id`؛ الأسئلة قابلة للتعديل في أي وقت.

**حالة الباك بعد إعادة القراءة الحية في 19 نوفمبر 2026:**

1. **اتصلح واتأكد:** `GET C/jobs/327` يرجع `answers` ومعرّفات الخيارات و`is_correct`، و`skills` و`mandatory_certifications`. القيم تظهر في الفورم والمعاينة. حماية `questionsIncomplete` مستمرة لأي بيانات ناقصة.
2. **لم يظهر في استجابة تفاصيل الوظيفة المختبرة:** `template_id`. ما زال مطلوبًا لربط السؤال المحفوظ بالقالب وقفل نصه ونوعه عند التعديل. علامة الـ chip ومنع التكرار بعد إعادة الفتح أصبحا يعملان من `is_used` في hints مع `job_id`. لا نعتبر كل سؤال نعم/لا قالبًا، لأن الأسئلة المخصصة تدعم النوع نفسه.
3. **يحتاج إعادة اختبار حفظ حي:** `question_templates[i][is_required]`. قراءة `is_required` تعمل وتعيد `false` و`true`، لكن هذا وحده لا يثبت دعم تعديل إلزام القالب في طلب الحفظ.
4. **لم يظهر في الاستجابة المختبرة:** `mark`؛ دعم حفظه ورجوعه يحتاج تأكيدًا إذا بقيت الدرجة ضمن النطاق.
5. **ما زال ناقصًا واتأكد:** القراءة العامة `GET U/jobs/327` ترجع 200، بدون `questions` و`assessment_id` (مطلوب للجزء 5). لم يُختبر الرد بحساب مرشح مسجل في هذه الجلسة.

## 4. المعاينة والمسودة والنشر والتعديل

**الحالة — 19 نوفمبر 2026:** استكمال الفرونت واختبارات المتصفح تمّا. قراءة البيانات كانت حية، واختبارات النجاح والفشل والحذف والنشر استخدمت اعتراض طلبات الحفظ واستجابات تجريبية؛ لذلك لا تُعد بديلًا عن دورة حفظ ونشر حية نهائية بعد تأكيد عقد القوالب.

| المكان                                 | الطلب / مصدر البيانات                                                                |
| -------------------------------------- | ------------------------------------------------------------------------------------ |
| فتح مسودة أو تعديل وظيفة               | `GET C/jobs/{id}`، باستجابة `{ data: { job } }`                                      |
| حفظ بيانات الخطوة الأولى أثناء التعديل | `POST C/jobs-update-step-one/{id}` مع `_method: put`                                 |
| حفظ وصف ومهارات وأسئلة تغيرت           | `POST C/jobs-step-two/{id}`                                                          |
| حفظ كمسودة / نشر                       | `POST C/jobs-step-three/{id}` مع multipart `status=draft` أو `open` واللغة الحالية   |
| المعاينة                               | القيم الحالية للفورم في الإنشاء والتعديل؛ تفاصيل التقييم الحقيقية من `assessment_id` |

**ما تم استكماله:**

- المعاينة لا تعتمد على رد حفظ قديم لعرض الوصف والمهارات؛ تعرض التغييرات الحالية حتى لو رد السيرفر لم يتضمنها كاملة. قسم Skills مخفي في المعاينة مع Other مثل الخطوة الثانية.
- `usePersistJobStepTwo` يحتفظ ببصمة آخر محتوى محفوظ لكل وظيفة. الانتقال للمعاينة، أو حفظ المسودة، أو تعديل بيانات الخطوة الأولى فقط، لا يعيد إرسال قائمة الأسئلة دون تغيير. هذا يقلل تبديل IDs غير الضروري لأن الباك يستبدل القائمة عند كل إرسال.
- فشل حفظ المحتوى يمنع تغيير الحالة وإظهار نجاح؛ ولا يتم تسجيل بصمة المحتوى كمحفوظة إلا بعد نجاح الطلب، فتعمل إعادة المحاولة.
- نجاح تحديث الخطوة الأولى أو الحالة يحدّث استعلامي تفاصيل الوظيفة وقائمة الوظائف. أزيلت إعادة التحديث المكررة من المكون.
- hints أصبحت خاصة بالوظيفة باستخدام `job_id` في الطلب ومفتاح الكاش، وتُحدّث بعد حفظ الأسئلة. تحقق حي للوظيفة 327 أثبت check للقالب المستخدم و`+` للقالب المتاح. تحقق المتصفح للإضافة والحذف المحليين نجح، وتحقق تحديث الحالة بعد الحفظ نجح باستجابة حفظ تجريبية، دون تغيير بيانات السيرفر.
- تحميل وظيفة للتعديل أو الاستكمال يتم عبر service مكتوب الأنواع و`apiFetch` و`getCompanyApiUrl`، دون `any`. الفشل أو الرد الفارغ يعرض حالة خطأ مترجمة وزر إعادة المحاولة بدل فورم فارغ قابل للحفظ.
- الشهادات الراجعة كنصوص تم التحقق من تحويلها الحالي؛ `BLS Certification` أُرسلت كنص، وليس معرّف سجل الشهادة على الوظيفة.

**التحقق:**

- القراءة الحية للوظيفة 327: 4 أسئلة بإجاباتها، 3 مهارات، شهادة، وتقييم 5. لا يظهر `template_id` أو `mark` في الأسئلة المقروءة.
- الانتقال للمعاينة دون تعديل: صفر طلبات حفظ محتوى. حفظ المسودة دون تعديل: طلب الحالة فقط.
- فشل حفظ المحتوى: لا طلب حالة ولا نجاح؛ إعادة المحاولة نجحت، والمعاينة عرضت الوصف المعدل رغم استخدام رد حفظ تجريبي قديم.
- فشل حفظ الحالة أو النشر: لا نافذة نجاح. الضغط مرتين عند النشر: طلب واحد بعد إعادة المحاولة.
- وضع تعديل المنشور: طلب الخطوة الأولى ثم الثانية للمحتوى المتغير، مع بقاء `assessment_id` خارج طلبات التعديل وعدم إرسال تغيير الحالة.
- حذف كل الأسئلة: طلب محتوى بدون مجموعتي الأسئلة ثم `status=draft`؛ إعادة الفتح من الاستجابة التجريبية أظهرت صفر أسئلة مع بقاء التقييم.
- وظيفة Other بلا أسئلة أو تقييم: لا Skills ولا مرفقات تجريبية في المعاينة. تحقق العربي على عرض 390px دون تمرير أفقي.
- فشل قراءة الوظيفة في وضعي `jobId` و`editId`: لا فورم قابل للحفظ، وإعادة المحاولة تسترجع العرض.
- `npx tsc --noEmit` وESLint للملفات المتغيرة والجديدة نجحا. `npm run lint` ما زال يعرض 9 أخطاء و34 تحذيرًا خارج التعديل؛ انخفض العدد بعد إزالة `any` من جلب وظيفة الشركة.

**المتبقي للتحقق الحي:** حفظ تعديل ثم إعادة قراءة الوظيفة ونشر/استكمال مسودة على السيرفر بعد تأكيد `template_id` وحفظ إلزام القالب. لا نثبت إصلاح نواقص الباك من استجابة تجريبية.

## 5. المرشح: عرض الوظيفة وإرسال أسئلة التقديم

**تحديث التنفيذ:** نُفّذت إزالة preview وتحويل الأسئلة وإرسال `answers` وCV وتحديث البيانات؛ الاختبار الحي بحساب مرشح لم يتم بعد. تفاصيل التحقق والحدود في قسم «استكمال فلو المرشح» أعلى الملف. الوصف التالي سجل المراجعة قبل التعديل، وليس وصف الكود الحالي.

**الموجود:** تفاصيل الوظيفة تُجلب من API، ويُسمح بالتقديم لحساب المرشح بعد تسجيل الدخول. تحميل CV البروفايل واختيار أو رفع CV للتقديم موجودان في التدفق، وطلب التقديم `POST U/jobs` موجود.

**الناقص:**

- `JOB_APPLY_PREVIEW_ENABLED = true`: عند غياب الأسئلة أو رجوع قائمة فارغة، تظهر تسعة أسئلة تجريبية. وعند غياب التقييم، يُستخدم تقييم `clinical-knowledge` التجريبي.
- يجب التعامل مع «لا توجد أسئلة / لا يوجد تقييم» كحالة صحيحة للوظيفة، وإزالة البدائل التجريبية من التدفق الفعلي.
- اعتماد mapper لأسئلة API وأنواعها واختياراتها، بحيث لا تُرسل UUIDs محلية أو معرّفات اختيارات `yes` و`no` بدل معرّفات إجابات السيرفر عندما يطلبها العقد.
- لا حاجة لبيانات الإجابات الصحيحة في واجهة المرشح؛ المطلوب فقط بيانات السؤال والاختيارات والإلزام التي يتيحها API لهذا الدور.

### فرق عقد التقديم

الكود الحالي يرسل FormData بالشكل المنطقي التالي:

```json
{
  "job_id": "101",
  "screening_answers": "[{\"questionId\":\"local-id\",\"selected\":[\"local-option-id\"]}]"
}
```

مثال الكولكشن يرسل JSON:

```json
{
  "job_id": 101,
  "answers": [
    { "question_id": 1, "answer_ids": [1] },
    { "question_id": 2, "answer_ids": [3, 5] }
  ]
}
```

إذًا التغيير المطلوب ليس اسم الحقل فقط: يلزم تحويل `questionId` إلى `question_id`، و`selected` إلى `answer_ids`، واستخدام معرّفات API، واعتماد encoding مدعوم مع CV الاختياري. تعليق `cv` داخل مثال JSON يجعله مثال طلب، وليس JSON صالحًا للنسخ حرفيًا دون إزالة التعليق.

بعد نجاح التقديم، يلزم تحديث بيانات الوظيفة والتقديمات وحالة التقييم؛ التنفيذ الحالي يضبط `hasApplied` محليًا، ولا يستدعي invalidation لهذه البيانات من `useApplyToJob`.

**الأدلة:** [جلب تفاصيل الوظيفة](../src/features/jobs/services/job-details-service.ts)، [البدائل التجريبية](../src/features/jobs/hooks/useJobApplyFlow.ts)، [شكل الإجابات المحلي](../src/features/jobs/types/job-apply.types.ts)، [طلب التقديم](../src/features/jobs/services/apply-job-service.ts)، [نجاح mutation](../src/features/jobs/hooks/useApplyToJob.ts).

### بعد التقديم

**تحديث التنفيذ:** أُوقف توليد الدعوة وتاريخها من الواجهة؛ النجاح يعرض التأكيد العام حتى يتوفر رد الدعوة الفعلي. النقاط التالية توثّق التنفيذ السابق والمطلوب لعقد الدعوة؛ الإسناد اليدوي مؤجل.

- يلزم تأكيد أن `POST U/jobs` ينشئ الدعوة ويرسل البريد تلقائيًا عند وجود تقييم، أو تحديد الآلية الفعلية لذلك. لا نضيف طلب دعوة يدويًا تلقائيًا بعد التقديم من دون عقد يؤكد الحاجة، لتجنب إرسال دعوتين.

| إجابة السؤال والانتقال  | `POST U/assessments/{id}/answer` مع `question_id` و`answer_ids` | حفظ الإجابة وانتظار النجاح قبل الانتقال أو قفل السؤال، وإتاحة إعادة المحاولة عند الفشل            |
| آخر سؤال / انتهاء الوقت | لا يوجد طلب إنهاء منفصل موثّق                                   | تأكيد هل آخر إجابة تغلق المحاولة، وكيف يُنفّذ التسليم عند انتهاء الوقت أو وجود أسئلة غير مجابة    |
| زيارة الرابط مرة أخرى   | سلوك القراءة / البدء يحتاج توثيق استجابة                        | استعادة حالة المحاولة والتقدم أو عرض أنها أُديت أو انتهت أو غير متاحة، بدل إعادة التقييم من الصفر |

**تفاصيل ناقصة يجب حسمها أثناء الربط:**

- شكل الاستجابة: هل البداية تعيد السؤال الحالي أم كل الأسئلة؟ وما الحقول التي تعيد رقم المحاولة والوقت المتبقي والدرجة والحالة؟
- مصدر deadline يجب أن يكون الوقت المعتمد من السيرفر، مع سلوك واضح عند refresh أو انقطاع الاتصال، بدل بدء مؤقّت جديد من `Date.now()`.
- هل حفظ الإجابة يقفل السؤال؟ وهل يسمح API بتعديلها؟ الواجهة الحالية تمنع العودة محليًا فقط.
- التمييز بين انتهاء وقت المحاولة وانتهاء صلاحية الدعوة وحدّ المحاولات، وترجمة أخطاء API إلى حالات `expired` و`taken` و`unavailable` وفق العقد الفعلي.
- عدد المحاولات ومدة صلاحية الرابط 72 ساعة لا تُعامل كحقائق backend لمجرد أنها ثابتة في UI. مثال إنشاء التقييم لا يوثّق حقلًا لعدد المحاولات أو مدة الدعوة.
- عدم عرض رسالة التسليم الناجح قبل تأكيد إغلاق المحاولة على السيرفر؛ لا نخترع endpoint مثل `/submit` أو `/finish` غير موجود في الكولكشن.
- التحقق من عرض مرفقات الأسئلة إذا أعادها API؛ نموذج سؤال المرشح الحالي لا يحتوي حقلًا للمرفقات، رغم وجود رفع مرفقات في أسئلة الشركة.

## 8. إكمال الحلقة: حالة التقييم للمرشح ومراجعة الشركة

### المرشح — `/candidate/applications`

- جلب التقديمات مربوط بـ `GET U/applications`.
- `ApplicationAssessment` عقد عرض مؤقت بحالات `pending/completed/expired`؛ لا توجد في الملفات المراجعة استجابة موثّقة تثبت أسماء هذه الحالات أو شكل الرابط.
- `ApplicationJobCard` لا يمرّر `assessment` إلى `ApplicationStatus` حاليًا، وعرض حالة التقييم ورابط أدائه داخل `ApplicationStatus` معطّل بالتعليقات.
- لهذا مسار «هعمل التقييم لاحقًا» لا يكتمل بمجرد الانتقال إلى صفحة التقديمات. المطلوب ربط الحالة والرابط الفعليين وإظهار إجراء الأداء عند صلاحيته.

**الأدلة:** [بطاقة التقديم](../src/features/jobs/components/candidate/ApplicationJobCard.tsx)، [عرض الحالة المعطّل](../src/features/jobs/components/candidate/ApplicationStatus.tsx)، [عقد العرض المؤقت](../src/features/jobs/types/candidate-applications.types.ts).

### الشركة — `/company/job/candidates/[slug]`

- قائمة المتقدمين للوظيفة مرتبطة بـ `GET C/applications/{jobId}`، والخدمة تحوّل بيانات `candidate.assessments` إن وُجدت.
- نافذة إجابات أسئلة التقديم تستخدم `CANDIDATE_ANSWERS_PREVIEW` لجميع الحالات، ولا تعرض إجابات التطبيق المحدد من API.
- المطلوب ربط إجابات التقديم بالسجل الصحيح وعرض الإجابة والدرجة إن كانت متاحة. endpoint منفصل لتفاصيل إجابات طلب واحد غير موثّق؛ يجب تأكيد هل تعود ضمن قائمة المتقدمين أو تفاصيل أخرى.
- `/company/assessments-results` وصفحة تفاصيل محاولة المرشح تستخدم بيانات تجريبية من `assessment-results` و`assessment-invitations` و`assessment-answers`، وليست نتيجة تسليم المرشح الفعلية.
- لا يوجد endpoint صريح لقائمة النتائج وتفاصيل المحاولات وإجاباتها في الكولكشن المراجع. وجود `GET C/assessments/{id}` أو `GET C/applications/{jobId}` وحده لا يثبت أنه يعيد هذه التفاصيل؛ يلزم استجابة فعلية أو توثيق للربط.

## 9. جزء إضافي غير مربوط داخل Post Job

**AI JD Builder:** في الخطوة الثانية يوجد مساعد كتابة وصف الوظيفة. الرسائل الأولية والاقتراح ثابتة، والإرسال يضيف رسالة محلية، والمرفقات روابط `blob:`، وApply ينسخ الاقتراح إلى الوصف. لم يوجد endpoint مخصص لتوليد وصف الوظيفة أو محادثة المساعد في الكولكشن. هذا بند مستقل يمكن تأجيله، ولا يمنع ربط الأسئلة والتقييم والتقديم.

**المهارات المقترحة:** تأتي من API المهارات الموجود بالفعل حسب المسمى، وليست مصفوفة mock مستقلة. لا يوجد ما يفرض endpoint ذكاء اصطناعي جديد لها لإكمال هذا الفلو.

**الأدلة:** [مساعد الوصف المحلي](../src/features/jobs/hooks/useAiJdBuilder.ts)، [مصدر المهارات المقترحة](../src/features/jobs/hooks/useRecommendedSkills.ts).

## نقاط تحتاج ردًا أو توثيقًا من الـ backend

1. استجابات فعلية لقراءة وظيفة الشركة والمرشح: شكل أسئلة القوالب والأسئلة المخصصة والاختيارات والتقييم، مع المعرّفات الأصلية.
2. تصحيح تكرار فهرس القوالب في مثال الخطوة الثانية، وقيم أنواع الأسئلة، ودعم `mark` وإلزام القالب، وآلية حذف الأسئلة وإزالة التقييم، وحفظهما في التعديل الشامل.
3. تأكيد أن طلب التقديم يعتمد `answers` كما بالمثال، ونوع المحتوى المقبول مع CV، وشكل استجابة الدعوة وحالة إرسال البريد.
4. هوية الرابط: تقييم أم دعوة أم محاولة، وطريقة ربطه بطلب التقديم الصحيح، خصوصًا إذا كان التقييم مستخدمًا في أكثر من وظيفة.
5. استجابات قراءة وبدء وإجابة التقييم، وآلية التسليم النهائية والتسليم عند انتهاء الوقت، وسياسة refresh والمحاولة المستمرة والمحاولات المتكررة.
6. مصدر نتائج الشركة وتفاصيل إجابات المحاولة وإجابات أسئلة التقديم، وحالة التقييم ورابطه داخل تقديمات المرشح.
7. سلوك endpoint الإسناد مع `user_ids[]` و`emails[]`، وendpoint إيقاف التقييم إن كان مطلوبًا. مساعد وصف الوظيفة AI يحتاج عقدًا مستقلًا إذا أُدرج في التنفيذ.
8. (من تنفيذ الجزء 1) إرجاع عدد التقييمات في التصنيف، وعدد الوظائف المرتبطة والدعوات الخارجية للتقييم، وتوحيد ترتيب الأسئلة بين `questions` و`assessments/{id}`، وتصحيح `has_file` في استجابة السؤال.

- [x] **تجهيز التقييم عند الشركة:** تم (الجزء 1). عقود الفئات والتقييمات والأسئلة مؤكدة.
- [ ] **1 — تثبيت العقود المتبقية:** استجابة `GET C/jobs/{id}` (company) و`GET U/jobs/{id}` (candidate) بجزء الأسئلة والتقييم، واستجابة `POST U/jobs`، وعقود أداء التقييم والنتائج (انظر "نقاط تحتاج ردًا").

- [ ] **6 — إكمال الحلقة:** حالة ورابط التقييم داخل تقديمات المرشح، وإجابات التقديم ونتائج المحاولة عند الشركة.

## سيناريوهات قبول الفلو بعد الربط

- [ ] وظيفة بلا أسئلة وبلا تقييم: لا تظهر بيانات تجريبية، ويُسجّل التقديم بدون مطالبة بتقييم.
- [ ] وظيفة بأسئلة فقط: تظهر الأسئلة المحفوظة، يُفرض الإلزام الصحيح، وتصل الإجابات إلى الشركة مرتبطة بالمرشح والوظيفة الصحيحين.
- [ ] وظيفة بتقييم فقط، ووظيفة بأسئلة وتقييم: يُحفظ الربط الحقيقي، وتُنشأ الدعوة حسب العقد مرة واحدة، ويعمل رابط الأداء.
- [ ] تعديل الوظيفة وإزالة بعض الأسئلة أو جميعها أو إلغاء التقييم: يرجع الوضع الجديد بعد refresh، بدون بيانات قديمة أو بدائل تجريبية.
- [ ] حفظ مسودة واستكمالها ثم نشرها: لا تفقد الأسئلة والتقييم، ولا تتكرر الوظيفة أو الأسئلة.
- [ ] اختيار «لاحقًا» بعد التقديم: يظهر رابط التقييم وحالته في صفحة التقديمات، ويصل المرشح إلى المحاولة الصحيحة.
- [ ] تقييم غير متاح أو منتهي أو أُدي سابقًا: تظهر الحالة الفعلية من السيرفر، ولا يمكن بدء محاولة غير مسموحة.
- [ ] فشل حفظ إجابة: يبقى السؤال متاحًا ولا تظهر رسالة تسليم ناجح؛ بعد refresh تُستعاد الحالة وفق سياسة السيرفر.
- [ ] آخر إجابة أو انتهاء الوقت: تُغلق المحاولة بالطريقة المعتمدة وتظهر النتيجة والحالة الفعليتان عند المرشح والشركة.
- [ ] اختبار الواجهة بالعربية والإنجليزية وعلى الموبايل، وحالات loading/empty/error/pending، ثم lint وTypeScript حسب قواعد المستودع.
